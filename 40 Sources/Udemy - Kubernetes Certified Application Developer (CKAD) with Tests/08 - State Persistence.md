# Section 8: State Persistence
## Lecture 122: Introduction to Docker Storage
- There are 2 concepts: Storage Drivers and Volume Drivers Plugins.
## Lecture 123: Storage in Docker
- When you install Docker on a system, it creates this folder structure at `/var/lib/docker`:
```bash
helios@helios-pc:~$ sudo ls /var/lib/docker
buildkit  containers  engine-id  image  network  plugins  rootfs  runtimes  swarm  tmp  volumes
```
> This is where Docker stores all its data (files related to images and containers running on the Docker host) by default. All files related to containers are stored under the containers folder, and the same to images. Any volumes created by the Docker containers are created under the volumes folder.
![[Pasted image 20260811142008.png]]
- Once the build is completed, you cannot modify the contents of these layers (read-only). You can only modify them by initiating a new build.
- When you run a container based off of the image using the `docker run` command, Docker creates a container based off of these layers and creates a new writable layer on top of the image layer. This layer is used to store data created by the container, such as log files written by the applications, any temporary files generated by the container, or just any file modified by the user on that container.
- The life of this layer is only as long as the container is alive.
- **Copy-on-Write (CoW) Mechanism:** When a process inside a container modifies a file belonging to the base image, the storage driver copies the file from the read-only image layer (`lowerdir`) to the container's writable layer (`upperdir`) before modifying it.
![[Pasted image 20260811145202.png]]
- If we wish to persist this data, we could add a persistent volume to the container:
	- First, create a volume using the `docker volume create <volume_name>` command. It creates a folder called `<volume_name>` under the `/var/lib/docker/volumes` directory.
	- Then, when I run the `docker run` command, I could mount this volume inside the Docker containers: 
```bash
docker run mysql -v <volume_name>:/var/lib/mysql
``` 
>In this case, `/var/lib/mysql` is the default location where MySQL stores data (This will also automatically create a volume if not created). So all data written by the database is in fact stored on the volume created on the Docker host. Even if the container is destroyed, the data is still active.

> This is called Volume Mounting as we are mounting a volume created by Docker under the `/var/lib/docker/volumes` directory.
- If we had our data already at another location (For example, we have some external storage on the Docker host at `/data` and we would like to store database data on that volume and not in the default `/var/lib/docker/volumes` directory), we would run a container using the command:
```bash
docker run mysql -v /data/mysql:/var/lib/mysql 
```
> This is called Bind Mounting.
### Preferred way
```bash
docker run mysql \
  --mount type=bind,source=/data/mysql,target=/var/lib/mysql
```
![[Pasted image 20260811151640.png]]
- Storage Drivers is responsible for all this operations. Docker uses this to enable layered architecture, some of the common storage drivers are:
	- AUFS: Default for Ubuntu but not available on other OS like Fedora or CentOS. In that case Device Mapper maybe a better option.
	- ZFS
	- BTRFS
	- Device Mapper
	- Overlay
	- Overlay2
> [!INFO]
> Overlay2 is now the default storage driver for modern Linux distributions (including Ubuntu, RHEL, Fedora, Debian, and CentOS). Drivers like AUFS and Device Mapper have been deprecated and removed from modern Docker Engine releases due to performance bottlenecks and kernel integration complexities.

> The selection of this depends on the underlying OS being used.
- Storage Drivers manage the read-write ephemeral container layer (using Copy-on-Write), whereas Volumes and Bind Mounts completely bypass Storage Drivers to write directly to the host filesystem (Volumes are not handled by storage drivers).
## Lecture 124: Volume Driver Plugins in Docker
- Volumes are handled by Volume Driver Plugins. The default Volume Driver Plugin is Local:
	- Local: It helps create a volume on the Docker host and store its data under the `/var/lib/docker/volumes` directory.
	- Azure File Storage
	- Convoy
	- DigitalOcean Block Storage
	- Flocker
	- Google Compute Persistence Disks (gce-docker)
	- GlusterFS
	- NetApp
	- RexRay: Can be used to provision storage on AWS, EBS, S3, EMC storage like Isilon and Scaleio or Google Persistence Disks or OpenStack Cinder.
	- Portworx
	- VMware vSphere Storage
```bash
docker run -it mysql \
  --name mysql \
  --volume-driver rexray/ebs
  --mount src=ebs-vol,target=/var/lib/mysql
```
## Lecture 125: Volumes in Kubernetes
- Just as in Docker, the pods created in Kubernetes are transient in nature. For this, we attach a volume to the pod. The data generated by the pod is now stored in the volume, and even after the pod is deleted, the data remains.
![[Pasted image 20260811160920.png]]
```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    run: rd-num-gen
  name: rd-num-gen
spec:
  containers:
  - command:
    - /bin/sh
    - -c
    - shuf -i 0-100 -n 1 >> /opt/number.out; sleep 3600
    image: alpine
    name: rd-num-gen
    volumeMounts:
    - mountPath: /opt
      name: data-volume
  volumes:
  - name: data-volume
	hostPath: 
	  path: /data
	  type: DirectoryOrCreate
```
## Lecture 126: Persistent Volumes
- A Persistent Volume is a cluster-wide pool of storage volumes configured by an administrator to be used by users deploying applications on the cluster. The users can now select storage from this pool using persistent volume claims.
![[Pasted image 20260811163206.png]]
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-volume1
spec:
  accessModes: 
    # Định nghĩa chế độ mount volume lên các hosts:
    # ReadOnlyMany (ROX), ReadWriteOnce (RWO), ReadWriteMany (RWX), ReadWriteOncePod (RWOP)
    - ReadWriteOnce # Chỉ cho phép 1 Node mount đĩa này ở chế độ Read-Write
  capacity:
    storage: 1Gi
  # LƯU Ý: hostPath KHÔNG dùng cho môi trường Production.
  # Nếu Pod bị terminated và scheduled sang Node khác, dữ liệu trên Node cũ sẽ không thể truy cập lại.
  hostPath: 
    path: /tmp/data
```

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-aws-volume1
spec:
  accessModes: 
    - ReadWriteOnce
  capacity:
    storage: 1Gi
  persistentVolumeReclaimPolicy: Retain # Giữ nguyên đĩa khi PVC bị xoá (Default). Delete, Recycle (Deprecated option)
  awsElasticBlockStore:
    volumeID: vol-0123456789abcdef0 # Điền AWS EBS Volume ID thực tế của bạn
    fsType: ext4
```

```bash
kubectl get pv
```

## Lecture 127: Persistent Volume Claims
- PV and PVC are 2 separate objects in the Kubernetes namespace. An admin creates a set of PVs, and a user create PVCs to use the storage.
- Once the PVCs are created, Kubernetes binds the PVs to claims based on the request and properties set on the volume. Every PVC is bound to a single PV (1 - 1).
- During the binding process, Kubernetes tries to find a PV that has sufficient capacity as requested by the claim, and any other request properties such as Access Modes, Volume Modes, Storage Class, etc. You could still use labels and selectors to bind to the right volumes.
- A smaller claim may get bound to a larger volume if all the other criteria matches and there are no better options.
- If there are no volumes available, the PVC will remain in a pending state until newer volumes are made available to the cluster.
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pv-volume1
spec:
  accessModes: 
    - ReadWriteOnce
  resources:
    requests:
      storage: 500Mi
```

```bash
kubectl get pvc

kubectl delete pvc pv-volume1
```
## Lecture 128: Using PVCs in Pods
Once you create a PVC use it in a POD definition file by specifying the PVC Claim name under persistentVolumeClaim section in the volumes section like this:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
    - name: myfrontend
      image: nginx
      volumeMounts:
      - mountPath: "/var/www/html"
        name: mypd
  volumes:
    - name: mypd
      persistentVolumeClaim:
        claimName: myclaim
```
The same is true for ReplicaSets or Deployments. Add this to the pod template section of a Deployment on ReplicaSet.

Reference URL: https://kubernetes.io/docs/concepts/storage/persistent-volumes/#claims-as-volumes

## Câu 1: Loại volume nào dùng để gắn Microsoft Azure Data Disk vào Pod?

* **Đáp án:** `azureDisk`
* **Giải thích chi tiết:**
`azureDisk` cho phép gắn trực tiếp một Azure Managed Disk (hoặc Unmanaged Disk) vào Pod dưới dạng block storage. Vì đặc tính của đĩa cứng vật lý/ảo trong môi trường Cloud, `azureDisk` hoạt động theo chế độ `ReadWriteOnce` (RWO), nghĩa là tại một thời điểm, Volume này chỉ có thể mount vào **duy nhất 1 Node** (và do đó chỉ dành cho 1 Pod hoặc các Pod cùng nằm trên Node đó).
* **Minh họa cấu hình:**
```yaml
volumes:
- name: azure-data
  azureDisk:
    kind: Managed
    diskName: myAzureDisk
    diskURI: /subscriptions/<sub-id>/resourceGroups/<rg>/providers/Microsoft.Compute/disks/myAzureDisk
    cachingMode: ReadWrite
    fsType: ext4

```


* **Góc nhìn DevSecOps & System Engineering:**
Dù `azureDisk` là định nghĩa gốc (in-tree volume plugin) trong Kubernetes, xu hướng hiện tại và thực tế sản xuất (production) đã chuyển sang dùng **Azure Disk CSI Driver** (`disk.csi.azure.com`). Các plugin in-tree đang bị khai tử (deprecated). Khi thiết kế hạ tầng DevSecOps trên AKS (Azure Kubernetes Service), bạn nên ưu tiên dùng `PersistentVolumeClaim` (PVC) kết hợp với `StorageClass` của CSI để đảm bảo tính linh hoạt và dễ bảo trì.

## Câu 2: Loại volume nào dùng để gắn một thư mục từ Node lưu trữ vào Pod?

* **Đáp án:** `hostPath`
* **Giải thích chi tiết:**
`hostPath` mount trực tiếp một file hoặc thư mục từ hệ điều hành của Node (Host Machine) vào bên trong Pod. Data này sẽ tiếp tục tồn tại trên Node ngay cả khi Pod bị xóa.
* **Minh họa cấu hình:**
```yaml
volumes:
- name: host-log
  hostPath:
    path: /var/log/app-logs # Đường dẫn trên Node
    type: DirectoryOrCreate

```


* **Góc nhìn DevSecOps & System Engineering:**
**`hostPath` là một nguy cơ rủi ro bảo mật nghiêm trọng (Security Risk)**. Nếu Pod bị chiếm quyền điều khiển (compromised), kẻ tấn công có thể truy cập, sửa đổi hoặc xóa các file hệ thống quan trọng trên Host Node (ví dụ: cSocket `/var/run/docker.sock` hoặc `/run/containerd/containerd.sock` để thực hiện *Container Escape*).
* **Quy tắc bảo mật:** Tránh dùng `hostPath` cho ứng dụng thông thường. Nếu bắt buộc phải dùng (ví dụ: triển khai DaemonSet thu thập log/metric như Fluentd, Promtail, Node Exporter), cần áp dụng chặt chẽ `PodSecurityAdmission` hoặc OPA Gatekeeper để giới hạn quyền `readOnly: true` và chỉ cấp quyền cho Service Account có đặc quyền.

## Câu 3: Loại volume nào lưu dữ liệu tạm thời gắn liền với vòng đời của Pod trên Node đó?

* **Đáp án:** `emptyDir`
* **Giải thích chi tiết:**
Khi Pod được gán vào một Node, một thư mục `emptyDir` rỗng sẽ được khởi tạo. Tất cả container trong cùng một Pod đều có thể đọc/ghi vào volume này. Khi Pod bị xóa khỏi Node (hoặc Node bị hủy), toàn bộ dữ liệu trong `emptyDir` sẽ bị xóa vĩnh viễn (**ephemeral storage**).
* **Minh họa cấu hình:**
```yaml
volumes:
- name: cache-volume
  emptyDir:
    medium: Memory # Lưu trữ trực tiếp trên RAM (tmpfs) để tối ưu I/O
    sizeLimit: 1Gi  # Giới hạn dung lượng tránh cạn kệt tài nguyên Node

```


* **Góc nhìn DevSecOps & System Engineering:**
`emptyDir` cực kỳ hữu ích cho các bài toán **Scratch space / Cache** hoặc làm bộ đệm trao đổi dữ liệu giữa Container chính và Sidecar Container (Pattern phổ biến trong microservices).
* **Lưu ý triển khai:** Nếu chọn `medium: Memory`, dữ liệu ghi vào sẽ tính vào RAM Limit của Pod. Luôn phải đặt `sizeLimit` cho `emptyDir` để tránh trường hợp Pod phình to dữ liệu tạm gây cạn kệt đĩa/RAM của Node, dẫn đến sự cố Node trạng thái `DiskPressure` hoặc `MemoryPressure`.

## Câu 4: Loại volume `fc` (Fibre Channel) dùng để làm gì?

* **Đáp án:** Gắn một Fibre Channel Volume có sẵn vào Pod.
* **Giải thích chi tiết:**
`fc` cho phép Kubernetes kết nối trực tiếp đến hệ thống mạng lưu trữ SAN (Storage Area Network) thông qua giao thức hạ tầng **Fibre Channel**. Dữ liệu từ SAN LUN (Logical Unit Number) có sẵn sẽ được mount trực tiếp vào Pod dưới dạng block storage.
* **Minh họa cấu hình:**
```yaml
volumes:
- name: fc-volume
  fc:
    targetWWNs:
      - "50060e801049ec00"
      - "50060e801049ec01"
    lun: 0
    fsType: ext4

```


* **Góc nhìn DevSecOps & System Engineering:**
`fc` volume thích hợp cho các mô hình On-Premises Data Center truyền thống, nơi doanh nghiệp đã đầu tư hạ tầng SAN đắt đỏ (IBM, Dell EMC, NetApp) và muốn dịch chuyển ứng dụng legacy (như các hệ quản trị CSDL lớn Oracle, DB2) lên Kubernetes mà không cần chuyển đổi định dạng lưu trữ.

## Số liệu so sánh tổng quan giữa các loại Volume

| Loại Volume     | Phạm vi dữ liệu (Lifecycle)        | Quyền truy cập phổ biến           | Use-case chính                                  | Mức độ rủi ro bảo mật                  |
| --------------- | ---------------------------------- | --------------------------------- | ----------------------------------------------- | -------------------------------------- |
| **`emptyDir`**  | Đi theo Pod (Xóa khi Pod xóa)      | `ReadWriteOnce`                   | Cache tạm, Scratch space, trao đổi giữa Sidecar | **Thấp** (Cần set `sizeLimit`)         |
| **`hostPath`**  | Đi theo Node (Giữ lại khi Pod xóa) | `ReadWriteOnce` / `ReadOnly`      | Log collector, System Agent (DaemonSet)         | **Rất cao** (Cần audit kỹ)             |
| **`azureDisk`** | Độc lập (Persistent Storage)       | `ReadWriteOnce`                   | Database, Stateful workloads trên Cloud Azure   | **Trung bình** (Cần phân quyền IAM)    |
| **`fc`**        | Độc lập (Persistent SAN)           | `ReadWriteOnce` / `ReadWriteMany` | Legacy On-Premises Enterprise Storage           | **Trung bình** (Phụ thuộc hạ tầng SAN) |

## Lecture 134: Why Stateful Sets?
- StatefulSets are similar to Deployment sets as in they create pods based on a template. They can scale up and scale down, perform rolling updates and rollbacks, but there are some differences:
	- Pods are created in a sequential order. After the first pod is deployed, it must be in a running and ready state before the next pod is deployed. It works in the reverse order when you scale it down
	- StatefulSets assign a unique original index to each pod, a number starting from 0 for the first pod and increments by one. Each pod gets a unique name derived from this index combined with the StatefulSet name.
	- Even if the pod fails and is recreated, it would still come up with the same name. StatefulSet maintain a sticky identity for each of their pods.

## Lecture 137: Storage in StatefulSets
![[Pasted image 20260812131827.png]]
- With StatefulSets. when you specify the same PVC under the pod definition, all pods created tries to use the same volume. It is file if that is what is desired (Not all storage types support that operation). 
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: google-storage
provisioner: pd.csi.storage.gke.io
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
parameters:
  type: pd-balanced
```

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  labels:
    app: postgres
  name: postgres
spec:
  replicas: 2
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - image: postgres:18.4-alpine3.24
        name: postgres
      volumeMounts:
      - mountPath: /var/lib/postgresql
        name: postgres-data
  serviceName: postgres-h
  volumeClaimTemplates:
  - metadata:
      name: data-volume
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: google-storage
      resources:
        requests:
          storage: 500Mi
```
> When the StatefulSet is created:
> - First, it creates the first pod, and during the creation of the pod, a PVC is created, the PVC is associated to a StorageClass, so the StorageClass provisions a volume on GCP, and then creates a PV and associates the PV with the volume and binds the PVC to the PV.
> - Then the second pod is created. It creates a PVC then the StorageClass provisions a volume on GCP, and then creates a PV and associates the PV with the volume and binds the PVC to the PV.
